# /learn dry run：三個真實問題跑下來，哪裡還太框架化

> `.claude/skills/learn/SKILL.md` 的第一次驗收。設計來源是
> [decision-learning-from-wondering](./decision-learning-from-wondering.md)，
> 但刻意**把那份的 schema 全部藏到後台**——前台只能看到一個會循序漸進教學的人。

**一句話結論**：檔位 0 和檔位 2 都成立，檔位 1 差點被我自己訂的「兩句」規則搞壞。
最有價值的一條規則不是流程，是**「這件要查」**——它在檔位 2 當場擋下一次 rot。

---

## 這份的效力邊界（先講清楚）

使用者的回應是**我模擬的**，不是真人跑的。所以這份能驗的是：

- ✅ 我會不會在該停的地方停（檔位 0 不擴寫）
- ✅ 規則之間會不會打架（發現一條）
- ✅ 內容品質夠不夠（三個問題都用 repo 既有 note 當底）
- ❌ **驗不了「使用者覺得負擔重不重」**——那要真人跑

真正的成功標準（比 chat 更容易搞懂、且不增加負擔）**這份還沒證明**，只證明了它沒有明顯的結構性缺陷。

## Dry run A（檔位 0）：skill 跟 slash command 差在哪？

**判檔位**：要改變他的判斷需要幾個他沒有的東西？0 個，他要的就是一個區別 → 檔位 0。

實際回答（全文，5 行）：

> 差在**誰決定要不要載入**。
> slash command = 一個 prompt 模板，你打 `/record` 它才跑，內容一次全塞進 context。
> skill = 一個帶 `description` 的資料夾，模型讀 description 自己判斷該不該上場，可以掛附檔等要用時才讀。
> 判準：想「自己叫它」→ command；想「它自己認出該上場」→ skill。
> 這個 repo 兩種都有——`/record` 是 command，`/meta-review` 是 skill。

**誘惑**：順便講 progressive disclosure 怎麼設計。忍住了。

**但這裡有個誠實的發現**：檔位 0 的表現跟普通 chat **一模一樣**。
skill 在這裡的價值是 0——它的工作就是不要上場。
所以如果它是自動觸發的，檔位 0 每次都要付約 5k token 的載入成本換零收益。

→ **這條直接決定了觸發方式。使用者當場裁：只吃 `/learn`，關掉自動觸發。**
description 已改成明文「只在使用者明確輸入 `/learn` 時才用；一般提問就算很模糊也不要自動套用」。
**接受的代價**：想不起來有這東西。緩解只有 README 日常節奏那一行，沒有別的機制。
**留下的觀察點**：檔位 0 在明確叫用下會變很稀有（誰會為了問事實打 `/learn`），
那一檔的規則變成保險而不是主路——但它只佔一行，留著。

## Dry run B（檔位 1 + 帶決策）：內部知識庫要不要從 RAG 換成直接讓 agent 搜檔案？

**判檔位**：3 件事 → 檔位 1。問句有「要不要」→ 加決策段。

開場（三行）：

> 你其實在問的是「我們這套 RAG 是不是白做了、換掉會不會更糟」。最少要懂三件事：
> ① 索引是第二份 state ② 共享的瓶頸不是檢索 ③ RAG 的真正門檻在哪。
>
> **① RAG 和直接搜的差別不在準確度，在你願不願意維護第二份 state。**
> 向量索引是原文的副本；原文一改索引就過期，你得自己補一條 reindex 流程。
> 直接 grep + 讀檔沒有這個副本，所以永遠新鮮。你們真正在付的成本很可能是「新鮮度」而不是「找不找得到」。

使用者挑戰「五千份文件 grep 不會太慢？」→ 直接答、不防衛、再拉回：

> 五千份 markdown 用 ripgrep 是毫秒級。慢的不是搜是**讀**——每次要把命中的幾份塞進 context，
> 那才是 token 和延遲。所以門檻不是「幾份文件」，是「一次查詢平均要讀幾份」。
>
> 回到第 2 件——**② 共享知識庫會爛掉的地方是寫入，不是查詢。**
> 多人同時讓 AI 改同一份會打架、過期的沒人清。RAG 一條都不解，它只解檢索。
> 所以「換不換 RAG」可能根本不是你們最痛的那題。

收一段 + 決策段：

> 所以：你們的問題八成不是「RAG vs 直接搜」，是「誰維護、什麼時候清」。
> 換成直接搜會馬上省掉 reindex 這條維護線，但不會讓文件自己變新。
>
> 現在我會先量兩件事再決定：平均一次查詢要讀幾份、全部文件塞不塞得進一次 context。
> 都在舒適區就換掉；如果查詢語意化程度高（同義詞多、關鍵字對不上）或延遲是產品需求，RAG 留著。

**發現（規則打架）**：我原本寫「檔位 1 的決策段就兩句」。實際寫出來是三句，而且三句才對。
**硬性字數是假精確**——寫「短」就好，寫死數字只會讓我為了守規則而刪掉有用的那句。

## Dry run C（檔位 2 + 投資 + 岔題）：記憶體這波我還能不能追？

**判檔位**：5 件事 → 檔位 2。有「能不能追」→ 加決策段。
底材是 repo 既有的 [memory-industry-map](./memory-industry-map.md) 和 [cxmt-dram-challenge](./cxmt-dram-challenge.md)。

開場把隱含目標講出來：「你問的其實是『我是不是已經錯過了，現在進去是接刀還是還有一段』」，
然後列五個標題、直接開講第一件：

> **① 這波漲的不是「需求變好」，是「供給被 HBM 吃掉」。**
> HBM 用 3D 堆疊，吃晶圓面積不成比例——占三巨頭 DRAM wafer input 約 22%，卻只產出約 9% 的 bit，
> 每 GB 吃掉 3–4 倍 DDR5 的晶圓。所以 AI 不只買走 HBM，還順手餓死了一般 DRAM 的供給。
> 意思是：你要追的信號在供給端，不是在 AI 需求的新聞。

**岔題測試**（使用者：「等一下，HBM 跟一般 DRAM 到底差在哪？」）——
直接答、不宣告「這是一個 branch」、答完半句話接回：

> HBM 是把多層 DRAM 疊起來、用矽穿孔接到 GPU 旁邊換頻寬。差別在**定價方式**：
> 一般 DRAM 是全行業一起漲跌的 commodity；HBM 是客製化 + 長約 + 預訂產能，
> 是唯一逃離 commodity 定價的那塊。一顆 AI GPU 的 BOM 裡它占 45–50%。
>
> 回到主線——**② 「記憶體」是三個市場，混在一起講必誤判。**

**最重要的一刻**（第 ③ 件，「這件要查」規則生效）：

> **③ 「能不能追」取決於你在週期哪一段——而這件我必須查，不能憑記憶。**
> repo 的記憶體地圖 freshness 標 2026-06、部分段落 2026-08，今天 9 月中，
> 那份的價格判斷已經是「當時的快照」不是「現在的事實」。
> 要判斷還能不能追需要三個即時數字：DDR5 現貨價這季的斜率、三巨頭最新 capex 指引、
> HBM 產能配置有沒有鬆。這三個我手上沒有。
> 前兩件是不會過期的框架，這一件是會過期的數字——你要我查我就去查。

**反事實檢查**（最後一步之後，不是考題）：

> 一個情境給你試試（想聽你怎麼看）：如果明天三巨頭同時宣布大幅擴 capex、股價當天大漲，
> 你覺得那對你這筆是好消息還是壞消息？

模擬使用者答「壞消息吧，供給要回來了」→ 「對，而且那正好是整條的重點：這波的燃料是供給紀律，不是需求故事。」

收束（節錄關鍵判斷 + 決策）：

**關鍵判斷（能帶去別的問題的）**
- 產業漲價先問「漲的是需求還是供給」——供給驅動的漲有明確結束訊號（產能回補），需求驅動的沒有
- 爆發性財報先扣掉「跟著漲價」那部分，再看有沒有搶到份額
- 新標的進來前先問「這跟我既有部位是不是同一條因果鏈」

**決策**
- 現在會怎麼做：拿到週期位階那三個數字之前不動。前四件不是「該不該進」的答案，是進去以後該盯什麼。
- 什麼事會讓我改主意：① 三巨頭任一家宣布顯著擴產 ② DDR5 現貨價月增率轉負 ③ CXMT 出現實質成本突破（成本新聞，不是產能新聞）
- 最便宜的下一步：只查一件——三巨頭最近一季法說的 capex 指引有沒有從「紀律」轉向「擴張」。

## 自評：哪裡還太重，刪了什麼

**這次刪掉的（判準：不寫也會發生的規則，不要寫）**

- 「他說跳過 → 跳掉」：模型本來就會。刪。
- 「他自己講出結論 → 那件算懂了往下走」：本來就會。刪。
- 「這個 skill 沒解決的」整節：對行為零影響，壓成開頭一句。
- 「不要做的事」六條 → 三條。把反膨脹閘套回自己身上才發現：那六條有五條是上面已經
  用粗體講過的重述（選單、考題、地圖只有標題）。留最容易犯、且上面只軟性講過的三條。

**這次加的（兩條，都來自 dry run 的實際毛病）**

- 超過 3 件就寫成條列，不要擠一行（C 的開場五個標題擠一行，手機上是一大坨）
- 反膨脹閘：**不寫「不寫也會發生」的規則**——這條是給未來維護這個 skill 的人的

**改的**

- 檔位 1 決策段「兩句」→「短」。硬性字數是假精確。

**本來要刪、dry run 證明該留的**

- **反事實檢查**：我原本覺得它最像考題、準備砍掉。C 跑下來它是最有價值的一刻——
  因為它接在最後一步後面、而且用「想聽你怎麼看」收尾，沒有考題感，
  還當場驗出使用者有沒有真的抓到主線。留。

**淨結果**：刪 3 段、壓 1 節、加 2 條規則。檔案從 99 行 → 97 行、5.3KB → 5.5KB。
**幾乎沒變小，這點要誠實講**——加的兩條規則跟刪掉的體積相抵。
真正的收穫不是變短，是留下來的每一條都通過了「不寫也會發生嗎」這一問。

**最有價值的一條規則**

不是任何流程，是**「需要即時數字就說『這個要查』，不要憑記憶講」**。
C 裡面它當場擋下一次 rot（拿 6–8 月的快照講 9 月的價格）。
這條是 CLAUDE.md 的缺陷分類直接長出來的，不是我想像的。

## 還沒解決的

1. **地圖是我猜的。** 「最少要懂的幾件事」由我判斷，我會猜錯。
   使用者打斷才是主要糾錯機制——所以寧可講短講快讓他有機會打斷。
2. **檔位判斷會漂。** 同一個問題我今天判 1、明天可能判 2。沒有校準機制，只有「寧可往低猜」。
3. **想不起來有這東西。** 只吃 `/learn` 換掉了誤觸成本，代價是它不會自己跳出來提醒你它存在——
   這跟那十幾個卡在分支、手機讀不到的主題是同一個死法。目前沒有緩解機制，只有 README 一行。
4. **decision 沉到哪裡沒定。** 目前是「照 CLAUDE.md 睡前步驟寫回 inbox/notes」，
   但決策要能被新證據更新（原始設計的第 7 條驗收），扁平 note 不好更新。
   先不動——等真的累積 2–3 個決策再看要不要有自己的位置。
